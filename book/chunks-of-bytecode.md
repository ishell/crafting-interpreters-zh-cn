# 字节码块

> 若你发现自己几乎把所有时间都花在了理论上，那就分出一些注意力给实践；它会改进你的理论。若你发现自己几乎把所有时间都花在了实践上，那就分出一些注意力给理论；它会改进你的实践。
>
> <cite>高德纳</cite>

我们已经有了一份完整的 Lox 实现——jlox，那么这本书为什么还没结束呢？一部分原因在于 jlox 倚赖于 <span name="metal">JVM</span> 替我们做大量工作。若我们想要弄清一款解释器**究竟**是如何一路到底地工作的，我们就需要亲手打造这些零零碎碎。

<aside name="metal">

当然，我们这第二款解释器仍然倚赖于 C 标准库来完成诸如内存分配之类的基本工作，而 C 编译器也让我们免于纠缠目标机器码的细节——天晓得，那段机器码或许还要靠芯片上的微代码来实现。而 C 运行时又倚赖操作系统来分页内存。但我们总得**在某个地方停一停**，否则这本书就塞不进你的书架了。

</aside>

之所以 jlox 还不够用，一个更为根本的原因是它**太慢了**。树遍历解释器对于某些高层、声明式的语言来说足以胜任。但对于一门通用、命令式的语言——哪怕是像 Lox 这样的"脚本"语言——它也飞不起来。看看下面这段小小的脚本：

```lox
fun fib(n) {
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2); // [fib]
}

var before = clock();
print fib(40);
var after = clock();
print after - before;
```

<aside name="fib">

这是一种**极其**低效的计算斐波那契数列的方式。我们的目标是想看看**解释器**跑多快，而不是想跑多快的程序。一段慢的、却做很多无用功的程序，正好是观察这一点的绝佳测试对象。

</aside>

在我这台笔记本上，jlox 要执行这段代码要花大约 72 秒。一段等价的 C 程序只需半秒。我们这种动态类型的脚本语言，永远不可能快过那种静态类型、手动内存管理的语言，但我们也不必甘心**两个数量级**以上的差距。

我们本可以拿着 jlox 跑在 profiler 之下，开始调优那些热点，但这也只能让我们走到这一步。它的执行模型——遍历 AST——从根本上就是错误的设计。你没办法把它精修到你想要的性能，正如你无法把一台 AMC Gremlin 改装成 SR-71 Blackbird 一样。

我们需要重新思考核心模型。本章将引入这一模型——字节码——并开启我们新的解释器 clox。

## 字节码？

在工程领域，几乎没有什么选择是毫无权衡的。为了更好地理解我们为何选择字节码，我们来让它与几种替代方案一较高下。

### 为什么不走 AST？

我们现有的解释器有几样拿得出手的优势：

*   首先，我们已经写好它了。它已经完工。事实上，它之所以能完工，主要是因为这种风格的解释器**写起来真的非常简单**。代码的运行时表示直接映射到语法本身。从语法分析器到我们在运行时所需的数据结构，几乎毫不费力。

*   它**可移植**。我们当前的解释器用 Java 写成，可以跑在 Java 所支持的任何平台上。我们也可以用 C、采用同样的思路来写一款新的实现，然后便可让它在几乎所有平台上编译并运行。

这些确实是优点。但另一方面，它**内存效率低下**。每一段语法都变成一个 AST 节点。像 `1 + 2` 这样微不足道的一条 Lox 表达式，会化为一堆对象加上一大堆指针链接在一起——大致是这么个样子：

<span name="header"></span>

<aside name="header">

那些"(header)"部分，是 Java 虚拟机用来支持内存管理、存储对象类型所维护的登记信息。它们也要占空间！

</aside>

<img src="image/chunks-of-bytecode/ast.png" alt="用以表示 '1 + 2' 的 Java 对象树。" />

每一根指针都要为该对象额外占用 32 或 64 位的开销。更糟的是，把数据如此分散地堆积在堆上、由一堆松散连接的对象拼凑而成，对<span name="locality">*空间局部性*</span>颇为不利。

<aside name="locality">

关于这同一问题，我曾在我第一本书《Game Programming Patterns》中专门用[整整一章][gpp locality]来讨论，若你愿意深挖的话。

[gpp locality]: http://gameprogrammingpatterns.com/data-locality.html

</aside>

现代 CPU 处理数据的速度，远远快于它们从 RAM 中拉取数据的速度。为了弥补这一点，芯片上有多层缓存。若 CPU 所需的一份内存正好已在缓存中，那么它就能被更快地加载。我们这里讨论的是动辄快上 100 **倍**的数字。

数据是如何进入这份缓存的呢？机器会替你做投机性的预取。它的启发式很简单：每当 CPU 从 RAM 中读取一份数据，它便会顺手把与之相邻的一小束字节一并拉入缓存。

若我们的程序接下来请求的数据恰好落在那条缓存行之内，那么 CPU 便会像工厂里润滑良好的传送带那般高速运转。我们**迫切希望**能利用这一点。要想高效地使用缓存，我们代码在内存中的表示应当是密集的、且能像被读取时那样有序排列。

再回过头看看那棵树。那些子对象可能栖身于<span name="anywhere">*任意*</span>的位置。树遍历器每一步若是顺着某个引用走到一个子节点，都可能踏出缓存的边界之外，迫使 CPU 暂停，待新的一份数据从 RAM 中咕嘟咕嘟地吸进来之后才能继续。仅凭这些对象所携带的指针字段与对象头所构成的**开销**，便足以把这些对象在内存中相互隔开、推出缓存之外。

<aside name="anywhere">

即便那些对象在语法分析器第一次产出它们时，恰好是按顺序被分配的，那么经过几轮垃圾回收之后——垃圾回收可能会在内存中挪动对象——它们最终落在哪里，便无从知晓了。

</aside>

我们的 AST 遍历器还背负着接口分派与访问者模式之类的开销，但光是局部性问题，便足以让我们去追求一种更优的代码表示。

### 为什么不编译成本地代码？

若你想**真**跑得飞快，你便想把那些层层间接统统搬到一边。直抵金属。机器码。它**听起来**就很快。**机器码**。

直接编译到目标芯片所支持的原生指令集，是那些最快的语言所采用的做法。目标原生代码，自打当年工程师们真的<span name="hand">亲手</span>用机器码写程序开始，便一直是效率最高的选项。

<aside name="hand">

是的，他们当年真的用**手**写机器码。写在打孔卡片上。那些卡片，想必是他们**用拳头**戳出来的。

</aside>

如果你从未写过任何机器码，或者它稍稍更人道一些的近亲——汇编代码——那么我便给你一个最温柔的入门介绍。原生代码是一连串密集的运算，直接以二进制编码。每一指令的长度在一字节到几字节之间，几乎低到令人窒息。"把一个值从这一地址移到那一寄存器。" "把这两寄存器里的整数相加。" 之类的操作。

CPU 一条接一条地执行这些指令，依次解码并执行。没有像 AST 那样树形结构，控制流是由从代码的一处直接跳转到另一处来处理的。没有间接，没有开销，没有不必要的绕来绕去，也没有追着指针跑。

快如闪电，但这种性能是有代价的。首先，编译成本地代码**绝非易事**。当今那些广泛使用的芯片，大多拥有庞大而拜占庭式的架构，指令堆了几十年攒下的家底。它们要求精妙的寄存器分配、流水线调度与指令调度。

此外，你当然也把<span name="back">可移植性</span>扔出了窗外。潜心钻研某一种架构若干年，所能得到的也仅仅是**若干种**主流指令集中**的一种**。若想让你的语言在它们**全部**上跑起来，你得学会所有这些指令集，并为每一种单独写一个后端。

<aside name="back">

情况也没有那么糟糕。一款架构良好的编译器可以让你跨不同架构共享前端与大部分中层优化 pass。主要是代码生成，以及围绕指令选择的一些具体细节，需要你为每一种架构从零写起。

[LLVM][] 项目便开箱即用地为你提供了其中的相当一部分。倘若你的编译器输出 LLVM 自己的那种特殊中间语言，LLVM 便进一步将其编译为多种架构的原生代码。

[llvm]: https://llvm.org/

</aside>

### 什么是字节码？

把这两点刻进你的脑子里。在一端，树遍历解释器简单、可移植，但慢。在另一端，原生代码复杂、平台相关，但快。字节码居于其间。它保留了树遍历器的可移植性——我们这本书里不会去与汇编代码打交道。它牺牲了**一些**简洁性以换取性能提升作为回报，但远不及完全走原生那条路的代价。

从结构上看，字节码颇似机器码。它是一连串密集、线性的二进制指令。这让它开销低、且对缓存友好。然而，它又比任何一**真实**的芯片都更简单、更高级。（在许多字节码格式中，每条指令只有一个字节长，这就是"字节码"这一名字的由来。）

想象一下，你正在为某种源语言编写一款原生编译器，而你被授予完全的自由，去定义一种**最简单**的目标架构。字节码便颇有几分那种意味。它是一种理想化的幻想指令集，让你这位编译器作者的生活更轻松。

对一种幻想架构的难题，当然在于它**并不存在**。我们通过编写一款**模拟器**——一段用软件编写的、用以一条一条地解释字节码的模拟芯片——来解决这一问题。若你愿意，不妨称之为**虚拟机**（**Virtual Machine**，**VM**）。

<aside name="p-code">

最早的字节码格式之一是 [p-code][]，它是为 Niklaus Wirth 的 Pascal 语言所开发的。你或许会以为，一台 15MHz 的 PDP-11 承担不起模拟一台虚拟机的开销。但彼时，正值计算机的寒武纪大爆发，新的架构层出不穷。跟上最新芯片的步伐，比起在每一种架构上榨取极致性能，更为要紧。这便是 p-code 中的"p"并非代表"Pascal"而是"portable"的原因。

[p-code]: https://en.wikipedia.org/wiki/P-code_machine

</aside>

这便将带我们走向我们新的解释器 clox。我们将追随 Python、Ruby、Lua、OCaml、Erlang 等主流实现的脚步。在许多方面，我们的 VM 的设计将与上一款解释器的结构平行：

<img src="image/chunks-of-bytecode/phases.png" alt="两款实现的阶段。jlox 是 Parser → Syntax Trees → Interpreter。clox 是 Compiler → Bytecode → Virtual Machine。" />

当然，我们不会按部就班地、按阶段顺序来实现。与我们上一款解释器一样，我们将在各章之间反复跳跃，一次添加一种语言特性。在本章中，我们将搭好整个应用程序的骨架，并创建存储与表示一段字节码所需的数据结构。

### 指令的动态数组

字节码是一连串指令。最终，我们还会在指令之外存储一些其它数据，因此让我们直接创建一个结构体来容纳这一切。

^code chunk-struct (1 before, 2 after)

此刻，它不过是一个字节数组的简单外壳。由于我们在编译一个块之前并不知道数组需要多大，它必须是动态的。动态数组是我最爱的数据结构之一。听起来这番话说出来就像"香草是我最爱的冰激凌<span name="flavor">口味</span>"，但请听我一言。动态数组能提供：

<aside name="flavor">

黄油山核桃仁其实才是我的最爱。

</aside>

* 缓存友好的密集存储。

* 常数时间的按下标访问元素。

* 常数时间的追加到数组末尾。

这些特性恰恰是 jlox 中我们披着 Java 的 ArrayList 类的外衣、一直在用的那些缘由。如今我们来到 C，便得自己动手滚一份出来。倘若你对动态数组有些生疏，它的思路颇为简单。除了数组本身，我们还维护两个数：数组中已**分配**的元素个数（"capacity"），以及那些已分配条目中**实际被使用**的数量（"count"）。

^code count-and-capacity (1 before, 2 after)

当我们添加一个元素时，若 count 小于 capacity，那么数组中尚有可用空间。我们将新元素直接放入那里，再将 count 加一。

<img src="image/chunks-of-bytecode/insert.png" alt="将一个元素存进一份仍有足够 capacity 的数组之中。" />

倘若我们已无剩余 capacity，那么流程便会稍复杂一些。

<img src="image/chunks-of-bytecode/grow.png" alt="在存放元素之前先扩容动态数组。" class="wide" />

1.  <span name="amortized">分配</span>一份更大的 capacity 的新数组。

2.  将既有元素从旧数组复制到新数组。

3.  存储新的 `capacity`。

4.  释放旧数组。

5.  将 `code` 更新为指向新数组。

6.  既然新数组有了空间，便将元素存入其中。

7.  更新 `count`。

<aside name="amortized">

在扩容时复制既有元素，看起来似乎让追加一个元素的动作变成 *O(n)*，而**不是**我上面所说的**O(1)**。然而，你只**偶尔**需要做这一复制步骤。大部分时候，已存在额外的容量，你无须复制。

要弄明白这是怎么回事，我们需要 [**摊销分析**](https://en.wikipedia.org/wiki/Amortized_analysis)。它告诉我们：只要我们按既有大小的一个固定倍数来扩容，那么当我们对一系列追加操作取平均时，每一次追加仍是 *O(1)*。

</aside>

<aside name="profile">

本书里我有点随意地挑了 8 这个数字。多数动态数组实现都有这样一个最小阈值。挑选一个恰到好处的值，应当**针对真实使用场景**进行 profiling，看哪一个常量能在额外扩容与空间浪费之间达成最佳折中。

</aside>

这听起来像是需要处理一长串的情形，但实现起来却很简单：

^code memory-c

当 `newSize` 为零时，我们亲手调用 `free()` 来处理去分配的情形。除此之外，我们倚赖 C 标准库中的 `realloc()` 函数。该函数恰好支持我们策略中的另外三种情形。当 `oldSize` 为零时，`realloc()` 等价于调用 `malloc()`。

有趣的情形发生在 `oldSize` 与 `newSize` 都不为零时。这些参数告诉 `realloc()` 去调整既有内存块的大小。若新的大小比既有内存块小，那它便仅仅**更新**该块的大小，并把你给它的那个指针原样返回。若新的大小更大，那它会试图将既有内存块扩容。

它**只有**在那块内存之后还**没有**被占用时才能这么做。若没有空间把那块内存扩容，`realloc()` 转而会去分配一份**新的**、所欲大小的内存块，将旧字节复制过去，释放旧块，然后返回指向新块的指针。记住，这恰恰是我们为动态数组所想要的行为。

由于计算机终究是有限的物质团块，而非计算机科学理论所预设的那种完美的数学抽象，分配可能因为内存不足而失败，`realloc()` 会返回 `NULL`。我们应当对此加以处理。

^code out-of-memory (1 before, 1 after)

当我们的 VM 拿不到所需的内存时，其实**也**没什么**实用**的事可做，但至少我们**能够**检测到这一点，并立即终止进程，而不是返回一个 `NULL` 指针，听凭它日后脱轨。

<aside name="shrink">

既然我们传入的仅是一段裸指针、指向那块内存的头一个字节，那么"更新"该块的大小**究竟**意味着什么？在底层，内存分配器为每一块堆上分配的内存都维护一份额外的登记信息，其中包括它的大小。

拿到一个指向某段已分配内存的指针，它便能找到这份登记信息——而这份信息对于干净地释放内存是必需的。正是这份大小元数据，`realloc()` 给它更新了。

许多 `malloc()` 的实现，都将已分配大小存储于**正好位于**返回地址**之前**的位置。

</aside>

## 常量

既然我们已经有了一个粗糙的 chunk 表示，便让我们让它变得更有用一些。我们可以在 chunk 中存放**代码**，但**数据**呢？许多解释器所要处理的值是在运行时、由运算的结果所创建的。

```lox
1 + 2;
```

值 3 在这里并没有出现于代码之中。然而，字面量 `1` 与 `2` 则存在。为了将这条语句编译为字节码，我们需要某种指令来表达"产生一个常量"，而那些字面量值需要在某处被存放在 chunk 之中。在 jlox 中，Expr.Literal AST 节点便承载了那个值。既然我们舍弃了语法树、换用了字节码，便需要换一种解法。

### 表示值

本章我们**尚未**真正**运行**任何代码，但由于常量同时横跨解释器的静态与动态两面，它迫使我们**至少**略略思考一下，我们的 VM 究竟应当如何表示值。

眼下，我们将尽可能从简——我们暂且只支持**双精度**浮点数。这一点日后显然会扩展，因此我们将设立一个新模块，为自己留出成长空间。

^code value-h

这个 typedef 抽象了 Lox 的值**具体**在 C 中如何表示。如此一来，我们便可以改变那种表示方式，而无须回头去修补那些传递值的既有代码。

回到该把常量存放在 chunk 哪一处的问题。对于像整数这样的小型定长值，许多指令集将值**直接**存放在操作码**之后**的代码流中。这些被称为**立即数指令**（immediate instruction），因为值的位元紧跟在操作码之后。

这种方式对于像字符串那样又大又变长的常量便不太好使。在一款针对机器码的原生编译器中，那些更大的常量会被存放在二进制可执行文件里一个独立的"常量数据"区中。然后，那条用于加载常量的指令便持有一个地址或偏移量，指向该常量在该区中的位置。

多数虚拟机都会做与这类似的事。比如，Java 虚拟机为每一个编译后的类关联了一个**常量池**（constant pool）。这听上去对 clox 来说已足够好。每个 chunk 都随身携带一份其程序中作为字面量出现的值的列表。为了<span name="immediate">简洁</span>起见，我们**所有**的常量都会放在那里，连简单的整数也不例外。

<aside name="immediate">

除了需要两类常量指令——一类用于立即数，一类用于常量表中的常量——立即数还迫使我们操心对齐、padding 与字节序。某些架构在试图将一个 4 字节整数塞入一个奇数地址时会不高兴。

</aside>

## 行信息

chunk 几乎囊括了运行时所需的来自用户源代码的全部信息。想到我们能将 jlox 里所创建的那一整个语法树类家族，压缩为一份字节数组与一份常量数组，简直令人难以置信。我们还**缺**一份数据。我们需要它，哪怕用户希望永远也看不到它。

当运行时错误发生时，我们向用户展示肇事源代码的行号。在 jlox 中，那些数字保存在 token 之中，而后者又存在 AST 节点里。既然我们如今抛弃了语法树、换上了字节码，便需要换一种解法。给定任意一条字节码指令，我们需要能够确定它**源自**用户源程序的哪一行。

有许多聪明的编码方式可供选择。我采用了所能想到的**最简单**<span name="side">不过</span> 的方法，即便它在内存上低效得令人脸红。在 chunk 中，我们存一份与字节码平行的整数数组。数组中的每一个数字，便是该字节码中所对应字节的行号。当运行时错误发生时，我们便在代码数组中以当前指令的 offset 为索引，查出对应的行号。

<aside name="side">

这种笨到家的编码方式**倒是**做对了一件事：它将行信息置于**独立的**数组，而非与字节码本身交织在一起。由于行信息仅在运行时错误发生时才会用到，我们**不希望**它出现在指令之间，霸占 CPU 缓存中的宝贵空间，并导致解释器在跳过去取它真正关心的操作码与操作数时引起更多缓存未命中。

</aside>

我们已拥有了一个三字节的 chunk。前两个字节是一条常量指令，用于从 chunk 的常量池中加载 1.2。第一个字节是 `OP_CONSTANT` 操作码，第二个是常量池中的索引。第三个字节（位于 offset 2 处）是一个单字节的 return 指令。

在剩余的章节中，我们将用更多种类的指令来充实这一切。但基本的结构已然就位，我们眼下已拥有了在运行时**完全**表示一段可执行代码所需的一切。还记得我们在 jlox 中定义的那一整个 AST 类家族吗？在 clox 中，我们已将其压缩为三份数组：代码字节、常量值、以及用于调试的行信息。

这种压缩，正是我们新的解释器会比 jlox 更快的关键所在。你可以把字节码视作对 AST 的一种紧凑序列化——为解释器在执行过程中按顺序反序列化它所**需要**的方式进行了高度优化。在[下一章][vm]中，我们便会看到虚拟机究竟是如何做到这一点的。

[vm]: a-virtual-machine.html

## 挑战

1.  我们对行信息的编码在内存上浪费得离谱。给定同一指令序列往往对应同一源代码行，一种自然的解决思路便是对行号进行类似[游程编码][rle]的方式。

    设计一种编码，用以压缩同一行上的连续指令的行信息。修改 `writeChunk()` 以写入这种压缩形式，并实现一个 `getLine()` 函数，给定指令的索引，便能确定该指令所在的行号。

    *提示：`getLine()` 不必十分高效。由于它仅在运行时错误发生时才会被调用，早已远离性能关键路径。*

1.  因为 `OP_CONSTANT` 的操作数仅占一个字节，一个 chunk 至多只能拥有 256 份不同的常量。这数目太小，写真实代码的人难免会撞上这天花板。我们可以使用两个或更多字节来存放操作数，但那样会让**每一条**常量指令占用更多空间。大多数 chunk 不会需要那么多唯一常量，因此为了支撑罕见情形而牺牲常见情形下的空间与局部性，得不偿失。

    为了在两种相互竞争的目标之间求得平衡，许多指令集都提供多条指令来完成同一操作，只是操作数的尺寸各不相同。保留我们现有一条字节的 `OP_CONSTANT` 指令不动，再定义第二条 `OP_CONSTANT_LONG` 指令。它将操作数存为 24 位整数，这应当绰绰有余。

    实现下面这个函数：

    ```c
    void writeConstant(Chunk* chunk, Value value, int line) {
      // Implement me...
    }
    ```

    它将 `value` 添加到 `chunk` 的常量数组中，然后写入一条恰当的指令以加载该常量。同时，也为反汇编器加上对 `OP_CONSTANT_LONG` 指令的支持。

    定义两条指令似乎两全其美。它**会**强迫我们做出哪些牺牲？

1.  我们的 `reallocate()` 函数倚赖于 C 标准库来完成动态内存分配与释放。`malloc()` 与 `free()` 并不魔法。找一两个开源的它们实现，并解释它们是如何工作的。它们是如何追踪哪些字节已被分配、哪些仍是空闲的？分配一块内存需要些什么？释放它呢？它们如何使这一过程保持高效？它们如何处理碎片化？

    *硬核模式：* 不调用 `realloc()`、`malloc()` 或 `free()` 来实现 `reallocate()`。你只被允许在解释器启动时调用**一次** `malloc()`，用来分配一大块内存，你的 `reallocate()` 函数能够访问它。从那块单独的区域中分出一些内存的小块——这便是你私人的堆。定义它**如何**这样做，是你自己的事。

## 设计笔记：测试你的语言

我们快走到书本一半的位置了，可有一件事我们**始终**没谈，那就是**测试**你的语言实现。这**并不**意味着测试不重要。我**再怎么**强调拥有一套良好的、完备的测试套件对你的语言**至关重要**都不为过。

我在写这本书的**任何一个字**之前，就为 Lox 写了一份[测试套件][tests]（欢迎你在自己的 Lox 实现上使用）。那些测试在我的实现中揪出了数不清的 bug。

[tests]: https://github.com/munificent/craftinginterpreters/tree/master/test

测试在所有软件中都很重要，但对于一门程序设计语言而言，它之所以尤为关键，至少有这么几条理由：

*   **用户期望他们的程序设计语言坚如磐石。**我们对成熟、稳定的编译器与解释器早已习以为常，以至于"那是你代码的问题，不是编译器的问题"已经[成了软件文化的一个根深蒂固的部分][fault]。如果你的语言实现里有 bug，用户得完整地走完悲伤的五个阶段，才能弄清究竟发生了什么——你**不会**想让他们去经历这一切。

*   **一门语言实现是一种深度互联的软件。**一些代码库**宽**而**浅**。倘若你的文本编辑器中文件加载的代码崩了，它 —— 但愿如此！—— 不会殃及屏幕上的文字渲染。语言实现则又**窄**又**深**，尤其是处理语言**实际**语义的核心部分。如此一来，由系统各部分之间古怪的交互所引发的潜在 bug 便容易悄然而至。要把它们逐一揪出来，需要扎实的测试。

*   **语言实现的输入，在设计上便是组合式的。**用户可以写出的可能程序是**无穷多**的，而你的实现需要让它们**全部**正确地跑起来。你显然无法穷尽地测试，但你需要努力覆盖输入空间中的尽可能多的部分。

*   **语言实现往往复杂、持续变化，且优化满身。**这便造就了代码的错综复杂，到处都是容易藏污纳垢的暗角。

[fault]: https://blog.codinghorror.com/the-first-rule-of-programming-its-always-your-fault/

这一切都在说，你**真的会很需要**大量测试。但**哪些**测试呢？我所见过的大多数项目都将主要精力放在端到端的"语言测试"上。每一项测试都是一段用该语言写的程序，以及它被期望产出的输出或错误。然后，你有一个测试运行器，将测试程序送进你的语言实现，并验证它**确实**做了它应该做的事情。用语言本身来写测试，这有不少好处：

*   这些测试**并不**与你的实现的任何特定 API 或内部架构决策相耦合。这让你得以自由地重组或重写解释器或编译器的部分，而无须同时更新一大堆测试。

*   你可以把同一套测试用于该语言的多种实现。

*   测试往往能够简洁、易读、易维护，因为它们**只是**你这门语言里的脚本。

事情也不全然是玫瑰色的：

*   端到端的测试能帮你判断**是否**存在 bug，但**不能**帮你定位 bug 究竟**在**哪里。倘若实现中的错误代码在哪里并不明显，便很难排查——因为测试所能告诉你的只是"正确的输出没出现"。

*   要精心雕琢一段**合法的**程序，恰好戳到实现中某个冷僻的角落，是件费力的事情。在高度优化的编译器中尤为如此——你可能需要写出绕来绕去的代码，才能**恰好**走到那条藏着 bug 的优化路径上。

*   启动解释器、解析、编译、运行每一条测试脚本，其开销可能都不小。一套庞大的测试套件——你**确实**想要——意味着**大量**时间被消耗在等待测试运行完毕上。

我可以继续罗列下去，但我不希望这篇变成一篇说教。我也不假装自己**懂得**如何去测试一门语言。我只是想让你记住**测试你的语言**是**多么**重要。说真的。测试你的语言。日后你会感谢我的。

</div>
