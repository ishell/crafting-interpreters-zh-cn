Garbage Collection

26 . 0垃圾回收

I wanna, I wanna,
I wanna, I wanna,
I wanna be trash.

The Whip，“Trash”

我们说 Lox 是一门“高级”语言，因为它让程序员不必操心那些与手头问题无关的细节。用户成了高管：把抽象目标交给机器，让卑微的计算机自己琢磨怎么到达。

动态内存分配正是自动化的绝佳人选。它是程序能跑起来所必需的，手工做又枯燥，而且还容易出错。不可避免的失误可能是灾难性的——崩溃、内存损坏，或安全漏洞。这种既冒险又无聊的活，机器比人拿手得多。

这就是为什么 Lox 是一门托管语言：语言实现替用户管理内存的分配与释放。用户执行需要动态内存的操作时，虚拟机自动分配。程序员从不操心释放任何东西。机器保证程序正在使用的内存会一直留着，直到不再需要。

Lox 提供了一种幻觉：计算机拥有无限内存。用户可以分配、分配、再分配，却从不想一想这些字节从哪儿来。当然，计算机还没有无限内存。托管语言维持这幻觉的办法，是背着程序员，把程序不再需要的内存收回来。干这活的组件，就叫垃圾回收器。

其实“回收利用”才是更好的隐喻。GC 并不是把内存扔掉，而是收回来给新数据再用。不过托管语言比地球日还古老，发明者只能用他们当时熟悉的那个比方。

26 . 1可达性

这就引出一个出人意料地难的问题：虚拟机怎么知道哪些内存不再需要？内存只有在将来会被读到时才需要；可若没有时光机，实现又怎能知道程序将执行哪些代码、将使用哪些数据？剧透：虚拟机不能穿越未来。于是语言做了一个保守的近似：只要一块内存有可能在将来被读到，就认为它仍在使用。

我说的“保守”是一般意义上的。另有一种叫“保守垃圾回收器”的东西，含义更具体。所有垃圾回收器在某种意义上都是“保守”的：只要内存可能被访问，就让它活着，而不是靠一只魔法八号球更精确地知道哪些数据将会被访问。

保守 GC是一类特殊收集器：只要某块内存里的值看起来可能是地址，就把它当成指针。这与精确 GC相对——我们要实现的正是后者——它确切知道内存里哪些字是指针，哪些存放的是数字或字符串之类的其他值。

这听起来太保守了。难道任何一点内存不都可能被读到吗？其实不然，至少在像 Lox 这样的内存安全语言里不是。举个例子：

var a = "first value";
a = "updated";
// GC here.
print a;

假设我们在第二行赋值完成后跑 GC。字符串 "first value" 仍坐在内存里，但用户程序再也没法碰到它。一旦 a 被重新赋值，程序就失去了对该字符串的任何引用。我们可以安全地释放它。若用户程序有某种办法引用某个值，该值就是可达的；否则，就像这里的字符串 "first value"，它就是不可达的。

许多值可以被虚拟机直接访问。看看这个：

var global = "string";
{
  var local = "another";
  print global + local;
}

在两个字符串刚拼接完、print 语句尚未执行时暂停程序。虚拟机可以通过翻找全局变量表、定位 global 的条目，到达 "string"。它可以通过走值栈、碰到局部变量 local 的槽位，找到 "another"。它甚至能找到拼接结果 "stringanother"——因为我们暂停时，那个临时值也正坐在虚拟机的栈上。

所有这些值都叫根。根是虚拟机无需经由其他对象中的引用就能直接到达的任何对象。大多数根是全局变量或在栈上，但我们很快会看到，虚拟机还有几处存放对象引用、并能自己找到的地方。

其他值可以通过另一个值内部的引用找到。类实例上的字段是最显眼的例子，但我们还没有那些。即便没有它们，我们的虚拟机仍有间接引用。考虑：

不过我们很快就会到那儿！

fun makeClosure() {
  var a = "data";

  fun f() { print a; }
  return f;
}

{
  var closure = makeClosure();
  // GC here.
  closure();
}

假设我们在标注那一行暂停程序并运行垃圾回收器。收集器结束后程序恢复，它会调用闭包，闭包进而打印 "data"。所以收集器必须不要释放那个字符串。但暂停时栈长这样：

"data" 字符串根本不在栈上。它已被抬离栈，移进了闭包所用的已关闭上值里。闭包本身在栈上。但要到达字符串，我们得穿过闭包及其上值数组去追踪。既然用户程序能够那样做，所有这些间接可访问的对象也被视为可达。

这就给出了可达性的归纳定义：

  • 所有根都是可达的。

  • 从可达对象引用到的任何对象，本身也是可达的。

这些是仍然“活着”、需要留在内存里的值。任何不符合这定义的值，都是收集器可以收割的正当猎物。那对递归规则暗示了一个我们可用来释放无用内存的递归算法：

  1. 从根出发，沿着对象引用遍历，找出全部可达对象的集合。

  2. 释放不在该集合中的所有对象。

如今有许多不同的垃圾回收算法在用，但它们大致都遵循同一结构。有的会交错或混合这些步骤，但两项基本操作都在。它们的差异主要在于如何执行每一步。

若想探索其他 GC 算法，The Garbage Collection Handbook（Jones 等）是权威参考。这么深、这么窄的话题，一本大书却相当好读。或许是我对“好玩”的观念比较古怪。

26 . 2标记-清扫垃圾回收

第一门托管语言是 Lisp——紧随 Fortran 之后发明的第二门“高级”语言。约翰·麦卡锡曾考虑过手动内存管理或引用计数，但最终选定了（并创造了）垃圾回收这个词——一旦程序内存不够，就回过头去找可以收回的未用存储。

约翰·麦卡锡在《History of Lisp》里写道：“一旦我们决定用垃圾回收，实际实现就可以往后推，因为当时只在做玩具例子。”我们把给 clox 加 GC 这件事往后拖，也是追随巨人的脚步。

他设计了最早、也最简单的垃圾回收算法，叫作标记并清扫（mark-and-sweep），或简称标记-清扫（mark-sweep）。在 Lisp 的最初论文里，其描述只占短短三段。尽管年代久远、简单朴素，同一基本算法仍是许多现代内存管理器的底子。计算机科学的某些角落，仿佛不受时间侵蚀。

顾名思义，标记-清扫分两个阶段：

  • 标记： 我们从根出发，遍历或追踪那些根所引用的全部对象。这是对所有可达对象的经典图遍历。每访问一个对象，就以某种方式标记它。（各实现对如何记录标记不尽相同。）

  • 清扫： 标记阶段一结束，堆上每个可达对象都已被标记。这意味着任何未标记的对象都不可达，正适合收回。我们遍历所有未标记对象，把每一个都释放掉。

看起来大致像这样：

追踪式垃圾回收器是任何沿着对象引用图去追踪的算法。这与引用计数相对——后者用另一套策略跟踪可达对象。

这就是我们要去实现的。每当我们认定该收回一些字节时，就会追踪一切、标记全部可达对象，释放没被标上的，然后恢复用户程序。

每当我们调用 reallocate() 去申请更多内存，就强制跑一次收集。那个 if 检查是因为 reallocate() 也会被用来释放或缩小一块分配。那种情况我们不想触发 GC——尤其因为 GC 自己也会调用 reallocate() 来释放内存。

就在分配之前收集，是把 GC 接入虚拟机的经典做法。你反正已经在调用内存管理器，挂钩代码很方便。而且，分配是你真正需要一些已释放内存以便复用的唯一时刻。若不用分配来触发 GC，就必须确保代码里每一个可能循环并分配内存的地方，也都有办法触发收集器。否则虚拟机可能陷入饥渴状态：需要更多内存，却永远不去收集。

更精巧的收集器可能在单独线程上跑，或在程序执行期间周期性交错——常常在函数调用边界，或发生向后跳转时。

26 . 4追踪对象引用

标记过程的下一步，是沿着对象之间的引用图去追踪，找出间接可达的值。我们还没有带字段的实例，所以含引用的对象不多，但确实有一些。尤其是，ObjClosure 有它关闭的 ObjUpvalue 列表，以及对它所包装的裸 ObjFunction 的引用。ObjFunction 又有一张常量表，装着函数体里创建的全部字面量的引用。这足以织出一张相当复杂的对象网，供我们的收集器去爬。

我把本章恰好插在书的这个位置，正是因为我们现在有了闭包，给垃圾回收器提供了有意思的对象去处理。

现在该实现那次遍历了。可以广度优先、深度优先，或别的顺序。既然我们只需要找出全部可达对象的集合，访问顺序大体上无关紧要。

我说“大体上”，是因为有些垃圾回收器会按访问顺序移动对象，于是遍历顺序决定了哪些对象最终在内存里相邻。这影响性能，因为 CPU 用局部性来决定把哪些内存预加载进缓存。

即便遍历顺序确实重要，也不清楚哪种顺序最好。很难断定对象将来会按什么顺序被使用，所以 GC 也很难知道哪种顺序有助于性能。

26 . 4 . 1三色抽象

收集器在对象图里游荡时，我们得确保它不会弄丢自己身在何处，或转圈转进死胡同。这对增量 GC 这类高级实现尤其要紧——它们把标记与运行用户程序的片段交错进行。收集器需要能够暂停，稍后再从停下的地方接着干。

为了帮我们这些脑子柔软的人类理解这复杂过程，虚拟机黑客们想出了一个叫作三色抽象的隐喻。每个对象有一个概念上的“颜色”，跟踪对象处于何种状态，以及还剩什么工作要做。

高级垃圾回收算法常常往这抽象里再加别的颜色。我见过多种灰色调，有些设计里甚至有紫色。我那篇紫褐-黄绿-品红-孔雀石收集器的论文，唉，未被接受发表。

  • 白： 在一次垃圾回收开始时，每个对象都是白色。这个颜色表示我们还完全没有到达或处理过该对象。

  • 灰： 标记期间，我们第一次到达某个对象时，把它加深成灰色。这颜色表示我们知道该对象本身可达、不应被收集，但尚未穿过它去看它引用了哪些其他对象。用图算法的术语说，这就是工作列表——我们知道但尚未处理的对象集合。

  • 黑： 当我们取出一个灰色对象、并标记它所引用的全部对象后，就把这个灰色对象变成黑色。这颜色表示标记阶段已处理完该对象。

用那套抽象来说，标记过程现在看起来像这样：

  1. 开始时全部对象为白。

  2. 找出所有根，把它们标成灰。

  3. 只要还有灰色对象，就重复：

    1. 挑一个灰色对象。把它提到的任何白色对象变成灰。

    2. 把原来的灰色对象标成黑。

我觉得把它可视化会有帮助。你有一张对象网，对象之间有引用。起初它们都是小白点。一旁有几条从虚拟机指向根的入边。那些根变成灰色。然后每个灰色对象的“兄弟姐妹”变灰，对象自身变黑。整体效果是一道灰色波前穿过图，身后留下一片可达的黑色对象。不可达对象未被波前触及，仍保持白色。

到最后，你得到一片已被到达的黑色对象之海，点缀着可被清扫并释放的白色对象小岛。不可达对象一旦释放，剩下的对象——全是黑的——会被重置为白，以备下一轮垃圾回收。

注意：在这过程的每一步，都没有黑色节点指向白色节点。这性质叫作三色不变式。遍历过程维持该不变式，以确保可达对象永远不会被收集。

add after traceReferences()
static void sweep() {
  Obj* previous = NULL;
  Obj* object = vm.objects;
  while (object != NULL) {
    if (object->isMarked) {
      previous = object;
      object = object->next;
    } else {
      Obj* unreached = object;
      object = object->next;
      if (previous != NULL) {
        previous->next = object;
      } else {
        vm.objects = object;
      }

      freeObject(unreached);
    }
  }
}
memory.c, add after traceReferences()

我知道这看起来像一大坨代码和指针把戏，但你走通一遍就会发现里面没多少东西。外层 while 循环走遍堆上每个对象的链表，检查它们的标记位。若对象已标记（黑），我们就放过它继续往前。若未标记（白），就把它从链表上拆下，用我们已经写好的 freeObject() 释放。

这里其余代码大多在对付一件事：从单链表删节点很麻烦。我们必须持续记住前一个节点，才能改它的 next 指针拆链，还得处理正在释放第一个节点的边界情况。除此之外，其实很简单——删掉链表里每一位都未置上的每个节点。

26 . 5 . 1弱引用与字符串池

收集差不多完成了。虚拟机还剩一个角落，对内存有些不寻常的要求。还记得给 clox 加字符串时，我们让虚拟机把它们全部驻留。这意味着虚拟机有一张哈希表，装着指向堆上每一个字符串的指针。虚拟机用它来给字符串去重。

在标记阶段，我们故意没有把虚拟机的字符串表当作根的来源。若那样做，就永远不会有任何字符串被收集。字符串表会越长越大，永远不把哪怕一个字节还给操作系统。那就糟了。

这可以是真实问题。Java 并不驻留所有字符串，但它驻留字符串字面量。它还提供 API 把字符串加进字符串表。许多年里，那张表容量固定，加进去的字符串永远无法移除。用户若对 String.intern() 不够小心，就会耗尽内存并崩溃。

Ruby 多年也有类似问题：符号——驻留的类字符串值——不被垃圾回收。两者最终都让 GC 能够收集这些字符串。

与此同时，若我们确实让 GC 释放字符串，虚拟机的字符串表就会留下指向已释放内存的悬空指针。那就更糟。

字符串表很特殊，我们需要对它的特殊支持。具体来说，它需要一种特殊的引用。表应当能引用字符串，但在判定可达性时，那条链接不应被视为根。这意味着被引用的对象可以被释放。一旦发生，悬空引用也必须修好——有点像一根会魔法般自我清空的指针。这套语义出现得够频繁，以至于有了名字：弱引用。

凭借标记时不遍历它这一事实，我们已经隐式实现了字符串表独特行为的一半。这意味着它不会强迫字符串可达。剩下的一半，是清掉已释放字符串留下的任何悬空指针。

要移除对不可达字符串的引用，我们需要知道哪些字符串是不可达的。这要到标记阶段完成后才知道。但又不能等到清扫阶段结束——那时对象及其标记位都已不在，无从检查。所以正确时机，恰好在标记与清扫两阶段之间。

26 . 6何时收集

我们现在有了一个功能完备的标记-清扫垃圾回收器。压力测试标志启用时，它会被不停调用；再打开日志，我们就能看着它干活，确认它确实在收回内存。可压力测试关掉时，它根本从不跑。该决定在正常程序执行中何时调用收集器了。

就我所见，文献对这问题答得不怎么样。垃圾回收器刚发明时，计算机只有一点点固定内存。许多早期 GC 论文假定你留出几千个字的内存——换句话说，几乎全部——一旦用完就调用收集器。简单。

现代机器有好几吉字节的物理 RAM，藏在操作系统更大的虚拟内存抽象后面，又与一大堆争夺各自那块内存的其他程序共享。操作系统会让你的程序要多少就申请多少，物理内存满了再从磁盘换入换出。你其实从不真正“用完”内存，只是越来越慢。

26 . 6 . 1延迟与吞吐量

再等到“不得不”才跑 GC，已不再合理，所以我们需要更微妙的时机策略。为了更精确地讨论，该引入衡量内存管理器性能时用的两个基本数字了：吞吐量与延迟。

与显式的、由用户编写的释放相比，每门托管语言都要付出性能代价。真正释放内存花的时间一样，但 GC 要花周期去弄清释放哪些内存。那是没有花在跑用户代码、做有用工作上的时间。在我们的实现里，那就是整个标记阶段。精巧垃圾回收器的目标，是把这开销压到最小。

有两个关键指标能帮我们更好理解这代价：

  • 吞吐量是花在跑用户代码与做垃圾回收工作上的时间总占比。假设你跑一个 clox 程序十秒，其中一秒在 collectGarbage() 里。那意味着吞吐量是 90%——90% 的时间在跑程序，10% 是 GC 开销。

    吞吐量是最根本的度量，因为它跟踪收集开销的总成本。其他条件相同，你想最大化吞吐量。直到本章之前，clox 根本没有 GC，因而有100%的吞吐量。这很难超越。当然，代价是：用户程序若跑得够久，可能耗尽内存并崩溃。你可以把 GC 的目标看成：修好那个“小毛病”，同时尽可能少牺牲吞吐量。

嗯，并不精确是 100%。它仍会把已分配对象放进链表，所以设置那些指针有一点点开销。

  • 延迟是用户程序因垃圾回收而完全暂停的最长连续时间块。它衡量收集器有多“成块”。延迟与吞吐量是完全不同的度量。

    考虑两次都跑十秒的 clox 程序。第一次，GC 只介入一次，在一次大规模收集里在 collectGarbage() 里整整花上一秒。第二次，GC 被调用五次，每次五分之一秒。花在收集上的总时间仍是一秒，所以两种情况下吞吐量都是 90%。但第二次运行里，延迟只有五分之一秒，比第一次少五倍。

这条柱表示程序的执行，分成跑用户代码的时间与花在 GC 里的时间。单次跑 GC 的最大时间片大小就是延迟。所有用户代码时间片加起来的大小就是吞吐量。

若你喜欢类比，想象你的程序是一家卖新鲜出炉面包给顾客的面包店。吞吐量是你一天能端给顾客的温热脆皮法棍总数。延迟是最倒霉的那位顾客要排队等到被服务多久。

跑垃圾回收器，就像暂时关掉面包店，把碗碟过一遍、把脏的和干净的分开，再洗用过的那些。在我们的类比里，没有专职洗碗工，所以这期间没有烘焙在进行。面包师在洗碗。

若每个人代表一个线程，一个显眼的优化就是让单独的线程跑垃圾回收，于是你得到并发垃圾回收器。换句话说，雇一些洗碗工在别人烘焙时清洗。非常精巧的 GC 就是这么工作的，因为它确实让面包师——工作线程——能几乎不被打断地继续跑用户代码。

不过需要协调。你可不想洗碗工从面包师手里抢碗！这协调增加开销和大量复杂性。并发收集器很快，但要正确实现很有挑战。

一天少卖几条面包不好，让某一位顾客干坐着等你洗完全部碗碟也不好。目标是最大化吞吐量、最小化延迟，但天下没有免费的午餐，面包店里也不例外。垃圾回收器在牺牲多少吞吐量与容忍多少延迟之间，做出不同取舍。

能做这些取舍很有用，因为不同用户程序需求不同。一个从一太字节数据生成报告的通宵批处理作业，只需要尽快做完尽可能多的活。吞吐量为王。与此同时，跑在用户智能手机上的应用需要始终立刻响应用户输入，好让屏幕上的拖动感觉丝般顺滑。应用不能在 GC 在堆里折腾时卡上几秒。

显然烘焙类比已经冲昏我的头了。

作为垃圾回收器作者，你通过对收集算法的选择，控制吞吐量与延迟之间的部分取舍。但即便在同一种算法内，我们对收集器运行频率也有很大控制权。

我们的收集器是停世界（stop-the-world）GC，意思是用户程序会暂停，直到整个垃圾回收过程完成。若我们等很久才跑收集器，就会堆积大量死对象。那会导致收集器运行时一次很长的停顿，因而延迟很高。所以，显然我们想非常频繁地跑收集器。

相比之下，增量垃圾回收器可以先收集一点点，再跑一些用户代码，再多收集一点，如此反复。

但每次收集器运行，都会花些时间访问活对象。那其实并没有做什么有用的事（除了确保它们不会被错误删除）。访问活对象的时间，既不是在释放内存，也不是在跑用户代码。若你非常频繁地跑 GC，用户程序甚至没有足够时间产生新垃圾给虚拟机收集。虚拟机会把全部时间花在执着地一遍遍重访同一批活对象上，吞吐量就会受损。所以，显然我们想非常不频繁地跑收集器。

事实上，我们想要中间某处；收集器运行的频率，是我们调节延迟与吞吐量取舍的主要旋钮之一。

26 . 6 . 2自适应堆

我们希望 GC 跑得够勤以最小化延迟，又够疏以维持像样的吞吐量。但当我们根本不知道用户程序需要多少内存、多频繁分配时，如何找到平衡？可以把问题甩给用户，暴露 GC 调参让他们自己选。许多虚拟机这么做。可若我们这些 GC 作者自己都不知道怎么调好，多半用户也不会。他们配得上合理的默认行为。

跟你说实话，这不是我的专长领域。我和不少职业 GC 黑客聊过——这是可以当作整个职业生涯来做的事——也读了大量文献，得到的答案全是……含糊的。我最终选的策略很常见、相当简单，而且（我希望！）对大多数用途够用。

想法是：收集器频率根据堆的存活大小自动调节。我们跟踪虚拟机已分配的托管内存总字节数。超过某个阈值时，触发一次 GC。之后，我们记下还剩多少字节内存——有多少没有被释放。然后把阈值调到比那更大的某个值。

结果是：存活内存变多时，我们收集得更少，以免为重访不断增长的活对象堆而牺牲吞吐量。存活内存变少时，我们收集得更勤，以免等太久而在延迟上输太多。

26 . 7垃圾回收的缺陷

理论上，我们现在全做完了。我们有了 GC。它周期性地介入，能收的收，其余留下。若这是一本典型教科书，我们会拍拍手掌上的灰，沐浴在我们造出的无瑕大理石大厦的柔光里。

但我不仅想教你编程语言的理论，还有有时很痛苦的现实。我要翻开一根烂木头，给你看底下住着的恶心虫子——而垃圾回收器的缺陷，确实是外面最恶心的无脊椎动物之一。

收集器的工作是释放死对象、保住活对象。两个方向都容易出错。若虚拟机未能释放不需要的对象，就会慢慢泄漏内存。若释放了正在使用的对象，用户程序就可能访问无效内存。这些失败往往不会立刻导致崩溃，使我们很难沿时间回溯找到缺陷。

更难的是，我们不知道收集器何时会跑。任何最终会分配一些内存的调用，都是虚拟机里可能发生收集的地方。就像抢椅子游戏。任何时刻，GC 都可能停下音乐。我们想保住的每一个堆分配对象，都得赶快找到一把椅子——被标成根，或作为引用存进某个其他对象——赶在清扫阶段来把它踢出游戏之前。

虚拟机怎么可能稍后使用一个对象——而 GC 自己看不见它？虚拟机怎么找到它？最常见的答案是：通过存在 C 栈某个局部变量里的指针。GC 走的是虚拟机的值栈与 CallFrame 栈，但 C 栈对它是隐藏的。

我们的 GC 找不到 C 栈里的地址，但许多能。保守垃圾回收器会搜遍内存，包括原生栈。这类里最出名的是 Boehm–Demers–Weiser 垃圾回收器，通常简称 “Boehm 收集器”。（在 CS 里成名的最短路径，是姓氏按字母排得很靠前，好在排序名单里最先出现。）

许多精确 GC 也会走 C 栈。即便那些，也得小心只存在于CPU 寄存器里、指向活对象的指针。

在前面几章，我们写过看似无意义的代码：把对象压进虚拟机的值栈，做一点活，再立刻弹掉。多数时候我说这是为了 GC 好。现在你明白为什么了。压与弹之间的代码可能分配内存，因而可能触发 GC。我们必须确保对象在值栈上，好让收集器的标记阶段找到它并让它活着。

我在把实现拆成章节、写散文之前，就写完了整个 clox 实现，所以有充足时间找到所有这些角落，冲掉其中大多数缺陷。本章开头放进的压力测试代码，以及一套相当不错的测试套件，都很有帮助。

但我只修了大多数。我留了几个，因为想让你尝尝在野外撞上这些虫子是什么滋味。若启用压力测试标志并跑一些玩具 Lox 程序，你大概能绊到几个。试试看，看你自己能不能修好几个。

26 . 7 . 1加入常量表

你很可能会撞上第一个缺陷。每个 chunk 拥有的常量表是动态数组。编译器往当前函数的表里加新常量时，数组可能需要扩张。常量本身也可能是堆分配对象，比如字符串或嵌套函数。

正被加进常量表的新对象传给 addConstant()。那一刻，对象只能在 C 栈上该函数的参数里找到。该函数把对象追加到常量表。若表容量不够需要扩张，它调用 reallocate()。那进而触发 GC，GC 未能标记新常量对象，于是在我们有机会把它加进表之前就把它清扫掉了。崩溃。

26 . 8挑战

  1. 每个对象顶部的 Obj 头结构体现在有三个字段：type、isMarked 和 next。它们占多少内存（在你的机器上）？你能想出更紧凑的办法吗？那样做有运行时代价吗？

  2. 清扫阶段遍历活对象时，会清掉 isMarked 字段，为下一轮收集做准备。你能想出更高效的办法吗？

  3. 标记-清扫只是众多垃圾回收算法之一。试着替换或增强当前收集器，探索其他算法。值得考虑的候选有：引用计数、Cheney 算法，或 Lisp 2 标记-压缩算法。

26 . 9设计笔记：分代收集器

若收集器长时间反复访问仍然活着的对象，就会损失吞吐量。但若它回避收集、堆积出一大堆垃圾再去蹚过，又会增加延迟。要是有办法分辨哪些对象可能长寿、哪些不会就好了。那样 GC 就可以少去重访长寿对象，更频繁地清理短命的那些。

事实证明，某种程度上有。许多年前，GC 研究者收集了真实运行程序里对象寿命的度量。他们在每个对象分配时跟踪它，最终在不再需要时再记一笔，然后画出对象往往活多久的图。

他们发现了所谓的分代假说，或更不客气的说法：婴儿死亡率。他们的观察是：大多数对象非常短命，但一旦活过某个年龄，往往就会再待相当久。对象已经活得越久，就越可能继续活下去。这观察很有力，因为它给了他们一个把手：如何把对象分成受益于频繁收集的，与不需要那么勤的两组。

他们设计了一种叫作分代垃圾回收的技术。工作方式是这样：每次分配新对象，它进入堆上一个特殊、相对较小的区域，叫作“托儿所”（nursery）。由于对象往往夭折，垃圾回收器会频繁地只对这片区域里的对象调用。

托儿所通常也用复制式收集器管理，它在分配与释放对象上比标记-清扫收集器更快。

GC 每对托儿所跑一轮，叫作一代。不再需要的对象被释放。活下来的现在被视为年长一代，GC 为每个对象跟踪这一点。若对象活过一定代数——常常只是单次收集——它就进入终身代（tenured）。此时它被复制出托儿所，进入大得多的、给长寿对象用的堆区域。垃圾回收器也会跑那片区域，但频率低得多，因为那些对象多半仍活着。

分代收集器是经验数据——对象寿命并非均匀分布这一观察——与利用该事实的巧妙算法设计的美妙联姻。概念上也相当简单。你可以把它想成两个分别调好的 GC，外加一套把对象从一处搬到另一处的相当简单的策略。
